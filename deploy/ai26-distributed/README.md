# AI26 three-machine distributed test

This directory contains the **public, secret-free orchestration contract** for issue #15. It does not contain the AI26 corpus, source/account lists, arena codebooks, researcher notes, credentials, hostnames or unpublished configuration.

The actual AI26 research configuration remains in the private repository and is supplied at runtime through `LACLAUGPT_PRIVATE_CONFIG_DIR`.

## Topology

| Machine | Collection | Analysis | Dashboard | Execution |
| --- | --- | --- | --- | --- |
| Laptop | Firefox/browser workflow | no | yes | interactive |
| CSC Roihu | no | yes | no | Slurm |
| Linux server | non-browser collectors | yes | yes | service/cron/systemd |

All three machines join the same `project_id=ai26` and the same `LACLAUGPT_RUN_ID`.

The shared planes are already defined by `docs/DISTRIBUTED_PROJECT_STORAGE.md`:

- MongoDB: durable canonical/queryable records, analyses, reviews, run metadata and artifact metadata.
- Redis: queues/streams, worker leases, locks, heartbeats and current configuration pointers. Redis is not the corpus source of truth.
- S3-compatible storage / CSC Allas: raw payloads, media and large artifacts.

## Public profiles

- `laptop.example.json`
- `roihu.example.json`
- `linux-server.example.json`

They conform to `schemas/distributed-run.schema.json`. They intentionally contain environment-variable **names**, not environment-variable values.

## Required runtime environment

Each participating host receives secret-bearing values outside Git:

```text
LACLAUGPT_RUN_ID
LACLAUGPT_MONGODB_URI
LACLAUGPT_REDIS_URL
LACLAUGPT_S3_ENDPOINT
LACLAUGPT_S3_BUCKET
LACLAUGPT_S3_ACCESS_KEY
LACLAUGPT_S3_SECRET_KEY
LACLAUGPT_PRIVATE_CONFIG_DIR
OLLAMA_HOST
```

The private config directory must provide the current private AI26 project/arena/source/codebook material. Public code should refer to those files by interface/path at runtime, never copy their contents into this repository.

Recommended worker IDs are ephemeral and descriptive, for example `laptop-<hostname>-<pid>`, `roihu-<slurm-job-id>` and `server-<hostname>-<pid>`. Do not use credentials, usernames or source names in worker IDs.

## Fixed analysis policy for this test

Analysis-capable hosts use:

```text
model = gemma4:12b
cloud_fallback = false
```

Each host talks to its own local Ollama service through `OLLAMA_HOST`. Do not configure a public shared Ollama endpoint.

Before processing, verify:

```bash
ollama list | grep -F 'gemma4:12b'
```

If the model is absent, the worker must fail before claiming durable work rather than silently using another model.

## Run identity and configuration freeze

Choose one run ID before starting any machine, for example a timestamp/slug generated by the researcher, and export the same value on every host:

```bash
export LACLAUGPT_RUN_ID='ai26-dist-<researcher-generated-id>'
```

At run start, the integration layer should write an `ai26__runs` manifest containing at least:

- `run_id`
- `project_id=ai26`
- schema version
- public module Git SHAs
- private AI26 configuration SHA-256 hashes
- private codebook/formation SHA-256 hashes
- model `gemma4:12b`
- cloud fallback disabled
- start time/status

Workers must compare these frozen values before claiming work. A worker with a mismatching config/codebook/model must refuse to join the run.

## Private configuration boundary

The public implementation must fail closed when `LACLAUGPT_PRIVATE_CONFIG_DIR` is missing or incomplete. It must not fall back to synthetic/public AI26 settings for a real distributed test.

Safe public behavior:

1. read the private file locally;
2. validate its expected interface;
3. compute/store a hash and revision in run provenance;
4. pass only the minimum required settings to the owning module;
5. never print the whole file, source lists or secrets to logs.

No private file should be uploaded to Redis merely because Redis is available. If a control document contains research-sensitive settings, retain the private deployment's access controls and distribute only what workers actually require. Durable private source material stays in approved private storage.

## Bounded integration test

This is not a full corpus run. Use a private test selection or `max_records_per_arena <= 10` from the examples.

The test should exercise all three arenas without publishing their private source selection:

- elites
- grassroots
- parliamentary

The public layer knows only the arena identifiers and hashes/revisions of the private configuration used.

## Coordination semantics

Use the existing Redis namespace `laclaugpt:ai26:*` and MongoDB project-prefixed collections from `docs/DISTRIBUTED_PROJECT_STORAGE.md`.

A safe claim protocol for the implementation modules is:

1. enqueue/reference a durable record using `project_id`, `run_id`, stable `source_url`, and durable record reference;
2. atomically claim a job using a Redis consumer group or lease;
3. persist claim/attempt metadata in MongoDB before expensive analysis;
4. periodically heartbeat the lease;
5. write analysis with an idempotency key based on `(project_id, run_id, source_url, analysis_version/config_hash)`;
6. persist the successful durable result before acknowledging/removing queue state;
7. if the worker dies, allow lease expiry and reclaim without creating a second durable result.

Redis loss must not erase the durable corpus or completed analysis state.

## Laptop procedure

1. Export the shared backend variables, `LACLAUGPT_RUN_ID` and private config directory in the local shell or an untracked secret manager/env file.
2. Start the Data Collection browser backend using the laptop machine profile.
3. Run the Firefox collector against the private bounded AI26 test selection.
4. Start Data Visualization against MongoDB/Allas for the same run ID.
5. Confirm new records become visible while Roihu/server workers update processing state.

The browser profile itself and browser session/cookies are private runtime state and must remain outside Git.

## CSC Roihu procedure

Use `roihu.sbatch.example` as a public skeleton. Site/project-specific account, partition, module loading, network/proxy setup and secret injection belong to private deployment configuration.

The job must verify Redis, MongoDB, Allas and local Ollama connectivity **before** claiming work. It then invokes the Data Analysis module's distributed worker entry point once that module implements the issue #15 adapter.

## Linux server procedure

Run three separable processes from the same profile/environment:

1. non-browser Data Collection worker/service;
2. Data Analysis worker using local `gemma4:12b`;
3. Data Visualization service.

A systemd/cron deployment may wrap those commands, but real unit files containing host paths, usernames, endpoints or Environment values are private deployment state. Public examples should use environment indirection only.

## Validation checklist

Before calling the integration successful, verify:

- laptop and server can write different collected records concurrently;
- Roihu and server can claim analysis work concurrently without duplicate durable results;
- killing one worker causes an expired claim to be safely reclaimed;
- retrying the same job is idempotent;
- both dashboards show the same `run_id` and shared processing state;
- records expose collection/worker/analysis provenance without exposing secrets;
- all analysis reports `gemma4:12b` and the same private config/codebook hashes;
- S3/Allas raw objects remain immutable/provenance-preserving;
- the four research-record layers remain visible through the shared data contract;
- local CSV/SQLite/filesystem modes remain separate valid development fallbacks.
