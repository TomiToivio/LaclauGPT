### What was wrong

The `#239` commit `1c995b6` added the `sak` feed and repointed the dormant Timnit Gebru Mastodon row
to `dair-community.social` **in the tracked plan**, but the runtime manifest
(`data/config/ai26.sources.toml`, mtime 2026-10-09 12:02) was last written *before* that merge and
was never re-deployed. So the hourly collector kept polling a handle whose last status is
2022-11-04 — four years below the study's 2026-09-01 publication floor, so it could never yield a
record — and never polled `sak` at all. Every cycle since the merge carried
`manifest_drift.in_sync = false`.

Confirmed from the live collector log, not only from the CLI: the 07:10 cycle emitted exactly the
`manifest_drift` block the issue quoted.

### What was done

```
scripts/deploy_ai26_sources.py --apply --allow-removals
Backed up previous manifest: data/config/ai26.sources.toml.backup-20261010T044551308854Z
Deployed tracked manifest:   data/config/ai26.sources.toml
```

Deployed from `origin/main` in an isolated worktree, so the shared checkout's checked-out branch was
not disturbed.

### The recurrence mechanism, stated plainly

The drift signal never failed and was never silent — it was emitted every hour and is how the issue
was found. What is absent is that **nothing acts on it**: the deploy is manual by design (#206 chose
detect-and-report over silent regeneration). A tracked-plan edit plus a forgotten redeploy therefore
produces a long-lived divergence. That policy was **not** changed unilaterally; wiring drift into the
daily maintenance run (or auto-deploying admission-only changes) is a maintainer call and is offered,
not assumed.
