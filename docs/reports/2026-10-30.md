### Root cause (unchanged, tracked as Collection #396)

The AI26 Allas bucket rejects every PUT with `QuotaExceeded`. Read access is fine. Bucket
usage measured in this run: **20,739 objects, 61.10 GiB**. Because the collector uploads
each raw envelope before writing the record, and because the analysis preflight refuses to
claim work when the object store is not writeable, capture and analysis have both been down
since **2026-10-28 19:05 EET** - now 35 consecutive failed cycles, not 11 as reported
yesterday.

Evidence gathered this run:

- 35 collection cycles end `runner_status=1 (tick partial/interrupted)`, each with
  `"status": "partial"`, `non_browser_records_collected: 30`, `non_browser_records_synced: 0`,
  every source outcome `reason: object_store_or_database_unavailable`.
- 35 analysis cycles end `ERROR: preflight reported a configuration problem; refusing to claim
  tasks`; preflight reports `"problems": ["object store unreachable", "object store is not
  writeable"]`, `"status": "invalid"`. Last successful cycle: 2026-10-28 19:29 (`status=0`).
- Shared store unchanged: 3,723 analyses, newest at 2026-10-28 17:16 UTC; 9,845 records,
  3,821 marked `ready`. No analysis has been produced for 35 hours.
- Thinking-model truncation counters are **flat** because no new records are being claimed
  (2,518 `structured generation truncated` and 3,556 `structured parse failed` lines are
  cumulative history, not this cycle). This confirms those lines are not the health signal.

### Deploy lag noticed (needs a decision, not a fix)

The running Collection checkout is **9 commits behind `origin/main`** (a60193e vs f75d14d),
detected by the wrapper's own runtime check on every cycle. Those 9 commits include the
#392/#393 capture-hygiene work (atomic raw captures, config fingerprint gate, and a
note that a quota failure must not stop capture). I deliberately did **not** fast-forward a
production capture checkout during an active quota outage: the same batch changes the
config-hash canonicalisation, and the #392 runbook is explicitly an operator procedure with
unverified three-host steps. This is a controlled-window deployment decision.

Separately: the #393 "quota failure must not stop capture" work covers the browser capture
server, which is idle on Laskin. The Laskin non-browser path still discards fetched records
when the upload fails, so roughly 30 records per cycle (~1,050 since 28.10.) were fetched and
lost with no local staging. Worth a follow-up design decision after the quota is restored.
