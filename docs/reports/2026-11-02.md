### Opened this run

**#413 (Data-Analysis) - X analysis dies in media staging: a non-S3 `source.raw_ref` raises `ValueError`
that is retried as transient.** The single X task seeded by #412 is claimed six times and writes no
result. The record exposes two object references: the valid `s3://` payload and a capture-side relative
path (`raw/x/.../capture-*.ndjson`) carried in `source.raw_ref`. `download_ref` refuses anything outside
the configured bucket with `ValueError`; `stage()` records it as `download_failed`, and because
`StagedObject.retriable` is defined as `status == "failed"`, the worker retries a permanent
classification error three times and parks the task. The operator message prints only a sha256 cache key,
so the log cannot name the refused reference. Scope: `source.raw_ref` is present and non-`s3://` on 9,984
stored AI26 records, so the same trap is armed corpus-wide; it only fires on records that carry a real
object next to the bad path.

Two candidate fixes are laid out in the issue and neither was implemented: normalising or dropping
non-absolute references plus a permanent-vs-retriable classification on the analysis side, or writing
`source.raw_ref` as a real object key on the collection side. Both change a contract, so they wait for a
decision.

## AI26 coverage gaps and source changes (2026-11-02, 16:00 EET)

### The non-browser strata stopped, and the ledger does not show it

The single most important finding of this run. Non-browser collection (web, bluesky, mastodon,
scholarly) has **stopped permanently** as of 2026-11-02 01:10, and every cycle since then reports
`status: ok`.

```
11-01 21:10 .. 11-02 01:10   non_browser_jobs_considered 6, records actually stored
11-02 02:10                  considered 6, collected 0   (partial, 6 errors)
11-02 03:10                  considered 4, collected 0   (partial, 4 errors)
11-02 04:10                  considered 3, collected 0   (partial, 3 errors)
11-02 05:10 .. 15:10         considered 0, collected 0   (ok)
```

Root cause, verified against the live queue and the code: `job_identity()` is `kind:name` (stable,
no epoch), `JobLeaseStore.enqueue()` writes `$setOnInsert` and `claim()` requires
`status == pending`, so the first successful run of a job is its last. All 34 queue documents were
created in the hour the shared-queue path went live (`cb3c429`, 2026-10-28 18:39); each ran once and
is now `done` (28) or `failed` (6). The queue, not the manifest, decides what is claimed, so
deactivating a row also does not retire its entry: the six `active = false` scholarly queries (#249)
kept being claimed and each exhausted three attempts on `unsupported_scholarly_backend` between
02:10 and 04:10.

Opened **#400 (Data-Collection)** with reproduction, the exact query and four design options. I did
not rewrite queue semantics and I did not re-arm the queue by hand: a blanket
`status -> pending` would also revive six rows that cannot work.
