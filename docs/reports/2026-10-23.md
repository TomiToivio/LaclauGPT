### 1. NEW AND BLOCKING: 40% of the analysis-grade corpus has no arena (issue #336)

The blank is not spread evenly; it is one capture path:

| platform | ready | blank arena |
| --- | --- | --- |
| x | 1,108 | **1,108 (100%)** |
| web | 216 | **200 (93%)** |
| rss | 987 | 26 |
| bluesky | 689 | 0 |
| arxiv | 265 | 0 |
| mastodon | 53 | 0 |

Yesterday's section recorded "x 43" ready records; the 2026-10-22 X backfill has now been
promoted into the analysis-grade set, so X went 43 → 1,108 and blank arena 70 → 1,334 in a
day. Two root causes, both verified in the store and the code:

- X capture envelopes never carry `arena` (and never carry `source.name`; only
  `source.author`). `count_documents({handoff.status:"ready", source.platform:"x",
  "source.raw_metadata.arena": {$exists:True}}) == 0`.
- The 200 blank-arena web records are all `provenance[0].module = "external-link-fetcher"`
  children of those X posts. `capture_server.py:390` gives a child the *parent's*
  `raw_metadata.arena`, so a parent without one propagates the blank.

The `groups:` block in `data/config/ai26.yaml` maps every X handle to an arena, and all 33
deployed manifest rows declare one; the mapping is used to build the tour URL list but is
never applied to the records the capture returns. **Why this is a blocking finding and not
a cosmetics item:** paper §4.1 compares the three arenas and §4.2 requires the evaluation
sample to be stratified over "the three arenas, source types, languages". A record with an
empty arena cannot enter that stratification, and 33% of the corpus is X. This is *not*
#322 — those rows were hollow and excluded; these have text (median 224 chars), pass the
floor, are analysed, and are counted. The `corpus-audit` CLI's `deferred_but_has_records:
["x"]` flag is the same fact seen from the other side.
