### The periodic report no longer completes (issue #423)

The Phase 1 periodic report has been terminated at its 900 s ceiling on **every**
cycle since 2026-11-05 17:45; the last completed report was 2026-11-05 15:50:36 and it
took 773 s, i.e. it was already sitting on the bound. Six ceiling events in a row, all
with `worker_status=0`, so the worker is not the problem.

Root cause, measured read-only on the live store:

* the previous-window lookup reads **every** summary the run has ever stored, purely to
  keep the newest one per scope: 136,218 documents, 1.3 GB, 9.6 KB average;
* fetching 2,000 of those payloads took 74.8 s, which projects to ~5,100 s for the full
  set — the read alone cannot fit in 900 s, and the collection only grows;
* the same 136,218 documents scanned through the two small fields the choice actually
  needs (`scope_key`, `window_end`) take 1.9 s.

This is the #416 defect class applied to `periodic_summaries`: #419 fixed the window
selection for `analysis_results` but left this lookup unbounded. Issue **#423** records
the measurements and the reproduction.

Fix (PR in Data-Analysis, `fix(#423)`): the lookup now scans the history through the
two-field projection, keeps at most the two newest candidate windows per scope, and
reads payloads only for those candidates. The window comparison stays a parsed-datetime
comparison, so stored string formats cannot reorder which window counts as previous,
and a window ending exactly at the boundary is still treated as the previous window.
New tests pin the bounded read and the four boundary cases; the Analysis contract
checks and the report test set pass.
