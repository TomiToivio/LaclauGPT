### The periodic report no longer completes (issue #423)

The Phase 1 periodic report has been terminated at its 900 s ceiling on **every**
cycle since 2026-11-05 17:45; the last completed report was 2026-11-05 15:50:36 and it
took 773 s, i.e. it was already sitting on the bound. Six ceiling events in a row, all
with `worker_status=0`, so the worker is not the problem.

Root cause, measured read-only on the live store:

* the previous-window lookup reads **every** summary the run has ever stored, purely to
  keep the newest one per scope: 136,218 documents, 1.3 GB, 9.6 KB average;
* fetching 2,000 of those payloads took 74.8 s, which projects to ~5,100 s for the full
  set — the read alone cannot fit in 900 s, and the collection only grows;
* the same 136,218 documents scanned through the two small fields the choice actually
  needs (`scope_key`, `window_end`) take 1.9 s.

This is the #416 defect class applied to `periodic_summaries`: #419 fixed the window
selection for `analysis_results` but left this lookup unbounded. Issue **#423** records
the measurements and the reproduction.

Fix (PR in Data-Analysis, `fix(#423)`): the lookup now scans the history through the
two-field projection, keeps at most the two newest candidate windows per scope, and
reads payloads only for those candidates. The window comparison stays a parsed-datetime
comparison, so stored string formats cannot reorder which window counts as previous,
and a window ending exactly at the boundary is still treated as the previous window.
New tests pin the bounded read and the four boundary cases; the Analysis contract
checks and the report test set pass.

### Why web and scholarly are still stopped: the tie, not the priority

New this run. Across all 24 cycles, `source_outcomes` contains **only** `bluesky_account`
(138 slots) and `mastodon_account` (12); not one `web_source` or `scholarly_query` slot in
144. The queue holds 15 claimable jobs at this moment, 13 of them never run (`attempts 0/3`).
Two verified defects, both in Data-Collection `350f0d9`:

1. **The claim order is an undefined tie.** Every job in `ai26__jobs` shares `priority: 1`
   (or 2) *and* an identical `created_at` of `1793205466.1429622`, so the claim's sort key
   `(priority, created_at)` (`distributed_jobs.py:307`) is a total tie across 22 P1 jobs and
   the tie-break falls to whatever plan Mongo chooses. Read-only replays of the *identical*
   filter and sort return different first jobs: with `limit=12`, `web_source
   microsoft_ai_blog` is first and six web rows occupy the top six; with `limit=1` - the
   `find_one_and_update` path the worker actually uses - `bluesky_account Creative Commons`
   is first. So the starvation is an ordering artefact, not a declared priority decision,
   and it can flip at any tick.
2. **`claim()` ignores `next_run_at`.** `release()` sets a recurring job back to `PENDING`
   with `next_run_at = now + poll` (`distributed_jobs.py:372-384`), but the claim query
   (`:282-294`) tests only status, attempts and capabilities. A job released after a failure
   is therefore claimable immediately and every hour afterwards, ahead of its cadence.
   Observed: `Creative Commons` sits `pending`, `attempts 1/3`, `next_run_at` in the future,
   and is claimed and then deferred for `tick_record_limit` in cycle after cycle - one of the
   six slots spent on work that cannot run.

With a 6-slot window against 10 hourly recurring account jobs, either defect alone is enough
to starve a stratum indefinitely while the collector reports `ok`. Recorded as a comment on
Data-Collection **#400** (the owning issue) rather than a duplicate; no new issue opened.
